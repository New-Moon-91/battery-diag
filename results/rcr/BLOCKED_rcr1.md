## B1. 16GB 카드 OOM — 해결됨 (`exact.py` 수정)

**증상**  `W=5, CAP≥3, NARR=4, prune=False, pu_all=True` 셀에서 정확해 진입 즉시

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 7.52 GiB.
GPU 0 has a total capacity of 15.51 GiB of which 7.47 GiB is free.
  File "src/battery_diag/exact.py", line 28, in __init__
    pr = torch.from_numpy(arrays['probs']).to(self.dev, dtype)
```

두 셀(`W5_cap3_narr4`, `W5_cap4_narr4`)이 이렇게 죽었다. GPU 0·1 각각에서 한 번씩.

**원인**  `ExactSolver.__init__` 이 CSR 열인덱스를 **무조건 int64 로 승격**하고 있었다.

```python
ix = torch.from_numpy(arrays['indices'].astype(np.int64)).to(self.dev)
```

`build.py` 는 `indices` 를 int32 로 만든다(`np.fromiter(..., np.int32, ...)`).
이 셀의 nnz 는 약 0.94e9 라서

| 배열 | 이전(int64) | 이후(int32) |
|---|---:|---:|
| col_indices | 7.5 GB | 3.8 GB |
| probs (f64) | 7.5 GB | 7.5 GB |
| **합** | **15.0 GB** | **11.3 GB** |

15.51GB 카드에 15.0GB + 부대 텐서 → 넘친다. 값 자체는 상태 인덱스(<nS=20,349)와
행 포인터(≤nnz)뿐이라 int32 로 충분하고 cuSPARSE 도 int32 CSR 을 그대로 받는다.
정밀도는 `probs`(float64)가 정하므로 **수치에 영향이 없다**.

**조치**  `nnz < 2^31-1` 이면 indptr·indices 를 int32 로 유지한다(커밋 `08c5c4a`).
`_policy_rows` 안의 누적합·`repeat_interleave` 만 int64 로 승격한다(길이 n_sa+1).

**검증**  `W4_cap3_narr4` 를 패치 후 다시 풀어 기존 `result.json` 과 대조:
`gstar` = 10243549.218335807 로 **차이 0.000e+00**, S2/S1/S2b/INDEX × (g, U_kwh,
L_total_kwh, dE_kg, forced_rate) **20개 필드 불일치 0 — 비트 단위로 같다.**
회귀 테스트 63 passed. 두 셀 모두 재실행 성공(각 490s/497s).

## B2. `metrics_w.stationary` 가 INDEX + 저리튬에서 200,000 회를 다 돈다 — **미해결, 우회**

**증상**  [3] 리튬 스윕의 `Li=8.16` 셀에서 shard 0 이 첫 셀에 30분 이상 머물렀다.
단일 프로세스 CPU 96%, **GPU 사용률 0%** — GPU 정확해가 아니라 numpy 구간이다.

**원인**  `W=4, Li=8.16, CAP=1, NARR=3` 으로 축소 재현해 정책별로 시간을 쟀다.

| 정책 | `stationary()` | 반환 시 잔차 |
|---|---:|---:|
| S1 | 0.6s | 9.73e-14 |
| S0 | 0.0s | 4.16e-17 |
| S2b | 0.0s | 4.16e-17 |
| **INDEX** | **342.4s** | **3.75e-13** ← tol(1e-13) 미달, itmax 소진 |
| S2 | 0.1s | 2.55e-14 |
| Bfast0/1/2 | 0.2s | 4.47e-14 |

**INDEX 만** 느리다. 그리고 잔차 3.75e-13 은 `tol=1e-13` 에 **도달하지 못한 채
itmax=200,000 을 소진했다**는 뜻이다. 저리튬에서 INDEX 가 유도하는 사슬의
부지배 고유값이 1 에 매우 가까워(느린 혼합) 멱승법이 기어간다.

**중요 — 결과는 맞다. 시간만 낭비된다.** 같은 셀의 수렴곡선을 실측했다:

| 반복 | 잔차 | 누적시간 | U_kwh | L_total_kwh | dE_kg |
|---:|---:|---:|---:|---:|---:|
| 100 | 2.499e-05 | 0.3s | 44.8913604397 | 62.1682791668 | 2954.850708 |
| 1,000 | 9.903e-06 | 2.1s | 44.8926247145 | 62.1682834381 | 2954.934020 |
| 10,000 | 4.572e-06 | 17.6s | 44.8931381328 | 62.1682834381 | 2954.967854 |
| 20,000 | 1.937e-06 | 34.4s | 44.8932636342 | 62.1682834381 | 2954.976125 |
| 50,000 | 1.474e-07 | 85.5s | 44.8933488873 | 62.1682834381 | 2954.981743 |

**반복 1,000회(2.1초)에서 이미 U 가 최종값과 7e-4 kWh 안에서 일치한다.** 논문이
보고하는 자리수(U 소수 둘째, dE 정수)보다 세 자리 이상 여유다. 나머지 199,000회
(340초)는 전부 낭비다.

**왜 고치지 않았는가**  `M.stationary` 의 판정을 손대면 **이미 계산한 24개 셀과
새 셀의 수렴 지점이 달라진다**(U 기준 ~1e-5 수준). 보고 자리수에는 안 보이지만
같은 표 안에 서로 다른 기준의 값이 섞이는 것은 피했다. 지금은 결과가 정확하고
시간만 손해라, **라운드 중 수치 기준을 바꾸는 위험보다 기다리는 편이 싸다**고 봤다.

**우회**  느린 셀(Li=8.16 × CAP=1,2)은 shard 0 에 남겨 두고, 나머지
(Li=25, 50 × CAP=1,2)를 유휴 GPU 1 에 별도 프로세스로 붙여 직렬화를 풀었다.
`run_rcr.py` 는 `DONE.json` 을 보고 건너뛰므로 중복 실행이 나도 결과는 같다.

**다음 라운드 권고**  `exact.py:evaluate` 가 2026-08-19 에 이미 같은 병을 고쳤다
(절대 tol 만 쓰다가 itmax 를 다 돌아 잡당 2,600초). `metrics_w.stationary` 에도
같은 **절대+상대** 판정을 넣되, **모든 셀을 같은 기준으로 재산출**해야 한다.
부분 적용은 표를 오염시킨다.

## B3. W=6 정확해 — rcr 정식화에서는 시도하지 않았다

[1] 은 W=4,5,6 × CAP=1,2 를 요구했으나 **W=6 은 W=4,5 만 산출하고 멈췄다.**
추정이 아니라 실측에 근거한 판단이다.

- `prune=True` W=6 은 (s,a) 15,496,916 / nnz 5.48e9 / CSR 65.8GB 였다(`DIGEST_w5.md`)
- rcr 정식화는 `prune=False, pu_all=True` 다. **W=4 에서 nA 가 201,000 → 273,572
  로 1.36배** 늘었다(실측). 같은 배율이면 W=6 은 nnz ≈ 7.5e9, CSR ≈ 90GB
- `build.py` 는 **in-RAM** 이다. indices(i32) 30GB + probs(f64) 60GB = 90GB >
  실장 62GB → OOM 이 확실하다. 디스크 여유도 168GB 뿐이다(캐시 659GB 를 뺀 나머지)
- 디스크로 내리려면 `streambuild` + `bigexact` 경로로 갈아타야 하는데, 이는
  `run_rcr.py` 를 고치는 일이고 [2]·[3] 을 끝내는 것보다 우선순위가 낮다
  (TASK 진행원칙: "[2] 까지만 돼도 성과다")

**따라서 [1] 의 W=6 행은 비어 있다.** W=4,5 만으로도 순위 역전은 관측됐다
(DIGEST [1] 참조) — W=6 은 방향을 바꾸지 않고 크기만 키울 것으로 보이나
**확인하지 않았다.** 필요하면 다음 라운드에서 streambuild 경로로 붙일 것.
